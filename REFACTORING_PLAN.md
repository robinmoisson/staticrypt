# StatiCrypt refactoring plan

This document lists areas of the codebase that could be improved, with specs for each. The
primary driver is **exposing StatiCrypt as a programmatic library** (`require("staticrypt")`)
while **preserving backward compatibility**. Secondary drivers are correctness, testability
and making it easier to land the pending performance PRs safely.

## 0. Backward compatibility contract

Before refactoring anything, it helps to be explicit about what "don't break things" means.
These are the surfaces that must keep working, roughly ordered by severity of breakage:

1. **Already-encrypted files in the wild must keep working.** Each generated HTML file embeds
   its own decryption code, so old files are self-contained — but two things reach across
   versions:
    - **Remember-me tokens and share links** store a *hashed* password (localStorage /
      `#staticrypt_pwd=`). The 3-round hash upgrade chain in `codec.decode` +
      `cryptoEngine.hashLegacyRound/hashSecondRound/hashThirdRound` exists solely for this.
      Any change to hashing or to `decode`'s retry logic must keep the chain intact
      (covered by `test/codec-compat.test.js` and the `encrypted-blobs` fixtures).
    - **`staticrypt --decrypt`** must be able to decrypt files generated by *any* previous
      version (it currently regex-extracts the payload from the generated HTML).
2. **CLI flags, defaults and config file.** All `staticrypt ...` invocations and
   `.staticrypt.json` (notably the persisted `salt`) must keep working.
3. **Custom password templates.** Users maintain their own templates. The template variable
   names (`/*[|template_title|]*/0`, `staticrypt_config`, `js_staticrypt`, ...) and the
   `staticryptJs.init(staticryptConfig, templateConfig)` browser API are public surface.
4. **The payload format**: `HMAC-hex(64) + IV-hex(32) + ciphertext-hex`, salt as 32-char hex,
   HMAC computed over the *hex string* of the ciphertext. Changing this changes what old
   share-link hashes can decrypt and what `--decrypt` can read — see §4 (format versioning).
5. **Deep requires.** `lib/` and `cli/` are shipped in the npm package, so
   `require("staticrypt/lib/cryptoEngine")` works today even though it's undocumented.
   Cheap to preserve: don't add a restrictive `exports` map (or use a wildcard passthrough).

Not compatibility surface (safe to change freely): everything in `scripts/`, the internal
shape of `cli/helpers.js`, internal function signatures inside `lib/` *as long as* the
browser-bundle build (`convertCommonJSToBrowserJS`) still produces working output.

## 1. Public programmatic API — the headline feature

### Current state

- `package.json` says `"main": "index.js"` but **no `index.js` exists** and it isn't in the
  published `files` list — `require("staticrypt")` throws today. The entry point is
  greenfield: we can design it without any compat constraint.
- All orchestration (hashing → encrypting → rendering the template) lives in
  `cli/index.js` + `cli/helpers.js`, interleaved with `process.exit`, `console.log`,
  prompts and filesystem access, so nothing is callable as a library today.

### Spec

Create a root `index.js` (matching the existing `main` declaration) exposing a small,
string-in/string-out API. No filesystem, no `process.exit`, no prompting, no `console` —
errors are thrown, I/O is the caller's job.

```js
const staticrypt = require("staticrypt");

// Encrypt an HTML string -> full password-prompt page as a string.
const { html, salt, hashedPassword } = await staticrypt.encrypt(inputHtml, password, {
    salt,                    // optional 32-char hex; generated (and returned) if omitted
    rememberDurationInDays,  // default 0; false to disable the remember-me box
    template,                // optional custom template *string* (not a path)
    templateStrings: { title, instructions, button, ... }, // mirrors --template-* flags
});

// Decrypt a generated page (equivalent of `staticrypt --decrypt`).
const { success, html } = await staticrypt.decrypt(encryptedHtml, password);

// Lower-level helpers, re-exported for advanced use:
staticrypt.generateRandomSalt();
await staticrypt.hashPassword(password, salt);
staticrypt.makeShareUrl(hashedPassword, baseUrl, { rememberMe }); // extracted from cli/index.js
```

Design decisions:

- **Strings in / strings out.** Batch, recursion, output directories, `.staticrypt.json`,
  password prompting stay in the CLI. This keeps the API surface tiny and lets the
  pending binary/perf refactors change internals freely behind it.
- **Template as a string, not a path**, so the API stays fs-free. Reading the default
  template from disk happens in the entry point once (`lib/password_template.html` ships in
  the package already).
- **One source of truth for defaults.** Extract the current yargs defaults
  (`DECRYPT` button label, colors, "Protected Page", ...) into `lib/defaults.js`, consumed
  by both `parseCommandLineArguments()` and the API. Today they only live inline in yargs
  options, so a programmatic caller couldn't reproduce CLI output.
- **Rewrite the CLI on top of the API** (see §2/§3) so it can't drift. CLI behavior stays
  bit-identical: same defaults, same generated output.
- **Ship `index.d.ts`** with types for the public API only. High value, zero runtime risk.
- **Versioning:** this is purely additive → a **minor** release.

### Tests

- Round-trip: `encrypt` → `decrypt` returns the input.
- Round-trip through the browser runtime: `encrypt` → load in jsdom → submit password
  (infrastructure already exists in `test/staticryptJs.test.js`).
- CLI-parity golden test: `staticrypt.encrypt` with fixed salt/password produces the same
  output as the CLI (modulo nothing, ideally).
- `npm pack` smoke test in CI: install the tarball, `require("staticrypt")`, call
  `encrypt`. This would have caught the broken `main` field.

## 2. Separate pure core from process-level side effects

### Current state

`cli/helpers.js` mixes three kinds of code:

- **Pure/lib-worthy logic**: `convertCommonJSToBrowserJS`, `buildStaticryptJS`,
  `getFullOutputPath`, salt validation.
- **Process-level side effects**: `exitWithError` (`process.exit(1)`) is called from *inside*
  `getFileContent`, `genFile`, `convertCommonJSToBrowserJS`, `writeFile`... A library must
  never do this.
- **Interactive I/O**: `prompt`, `validatePassword`, `getPassword` (env/CLI/stdin).

There are also two latent bugs worth fixing on the way:

- `copyFile`'s catch block references `filePath`, which is **undefined in that scope**
  (`cli/helpers.js:297`) — any copy failure throws a `ReferenceError` that masks the real
  error.
- `runStatiCrypt()` is called without `.catch()` (`cli/index.js:232`) — any rejection is an
  unhandled promise rejection, with a confusing stack and (on older Node) exit code 0.

### Spec

- Move lib-worthy pieces into `lib/` and make them **throw** instead of exiting:
  - `lib/bundler.js`: `convertCommonJSToBrowserJS`, `buildStaticryptJS` (needed by the API
    to build the injected JS; memoize the result — it's deterministic per version).
  - Errors: throw plain `Error`s (or a `StaticryptError` subclass if we want
    programmatic discrimination — start with plain `Error`, add the subclass only if the
    API needs it. Keep it simple).
- The CLI keeps `exitWithError`, but it's only called from the top level:
  `runStatiCrypt().catch((e) => exitWithError(e.message))`. Helper functions bubble errors
  up instead of exiting mid-flight.
- `prompt` / `getPassword` / `validatePassword` stay CLI-only (they read stdin/env — fine).
- Keep re-exporting moved functions from `cli/helpers.js` (one-line aliases) since `cli/` is
  shipped in the package and deep-requires are possible. Cheap insurance.

Effort: small. Risk: low (behavior-preserving; the CLI e2e tests cover the output paths).

## 3. Fix the async traversal in the CLI

### Current state

`recursivelyApplyCallbackToHtmlFiles` calls `encodeAndGenerateFile`/`decodeAndGenerateFile`
— both `async` — **without awaiting them** (`cli/index.js:114-122, 153-169`):

- An error in any file (unreadable template, write failure once they throw instead of
  exiting per §2) becomes an unhandled rejection; other files may or may not have been
  written; exit code doesn't reflect failure.
- Output ordering and "did everything finish before we returned" are accidental — it only
  works today because the final writes are sync and errors call `process.exit` directly.

### Spec

Split traversal (pure) from execution (async):

```js
// pure & unit-testable: walk inputs, classify html vs asset files
collectFileOperations(inputPaths) -> [{ type: "encrypt"|"copy", inputPath, rootDir }]

// cli/index.js
for (const op of operations) { await handle(op); }   // sequential, deterministic, awaited
```

- Sequential `await` keeps memory bounded (one file in memory at a time — matters given the
  large-file issues in #213) and makes failures deterministic. Parallelism is not worth the
  complexity here; encryption is CPU-bound in a single-threaded runtime anyway.
- Decide and document per-file failure policy: fail fast (recommended: predictable, and
  matches current `exitWithError` behavior) — but now with a correct non-zero exit code.
- `recursivelyApplyCallbackToHtmlFiles` is exported; keep a thin compatibility wrapper in
  `cli/helpers.js` delegating to the new function.

Effort: small-medium. Risk: low, and `test/cli-e2e.test.js` already covers recursion.

## 4. Payload extraction + format versioning module

### Current state

- The CLI decrypt path regex-scrapes the generated HTML for
  `"staticryptEncryptedMsgUniqueVariableName": "..."` and the salt (`cli/index.js:177-178`).
  The knowledge of "how a generated page stores its payload" is duplicated between the
  encode path (template data assembly, `cli/index.js:214-223`), the decode regexes, and
  implicitly the browser runtime.
- Two open PRs (#229 base64 storage, #231 compression) **change the payload format**. As
  written they'd break `staticrypt --decrypt` on old files and complicate the compat story,
  because there's no format version to branch on.

### Spec

Create `lib/payload.js` as the single owner of the embedded-payload format:

```js
buildStaticryptConfig({ encryptedMsg, salt, isRememberEnabled, rememberDurationInDays })
    // -> the object embedded in the template (adds formatVersion going forward)
extractStaticryptConfig(html)
    // -> { encryptedMsg, salt, formatVersion } | null  (handles versionless legacy pages)
```

- Used by the API `decrypt`, the CLI `--decrypt`, and the encode path.
- Add a `formatVersion` field to newly generated configs (absent ⇒ treat as version 1).
  This is invisible to the browser runtime (each page carries its own decoder) but lets
  `decode`/`--decrypt` and future formats (base64 payloads, compressed payloads) branch
  cleanly instead of guessing.
- **Rule to enforce from then on:** decode paths must accept *all* previous versions; new
  fixtures are added to `test/fixtures/` for each format bump (generated pages from released
  versions, not just crypto blobs — extend `test/fixtures/generate.js`).

This is the piece that makes PRs #229/#231 mergeable without a compat cliff.

Effort: small. Risk: low.

## 5. Codec & crypto engine internals (aligned with the open PR series)

There's a coherent series of community PRs (all by @jimhark) touching this layer. Rather
than reviewing them piecemeal, sequence them behind the API façade from §1 so internal
signatures can change without breaking anyone:

| PR | What | Recommendation |
|----|------|----------------|
| #227 | `decode()` recomputes the HMAC per backward-compat retry; also unwinds recursion | Take first. Small, real perf win, no format change. The iterative rewrite also makes the hash-upgrade chain easier to read. Covered by existing compat tests. |
| #214 | Node `Buffer`-based hex stringify (fixes `RangeError` on large files, #213) | Note: its head commit is **identical to #219's** — it's the same branch content. Treat #214 as superseded by #219 (or cherry-pick just the HexEncoder change as a low-risk standalone fix). |
| #219 | Use `Uint8Array` internally instead of hex strings | The big one: large-file memory/speed. Land **after** §1 freezes the public API as strings. Critical constraint: the HMAC is computed over the *hex string* of the ciphertext — verification of existing files must keep hashing those exact bytes. The `encrypted-blobs` fixtures guard this; add a large-file fixture too. |
| #221, #223, #225 | Small cleanups (HexEncoder polish, `getRandomAlphanum`, naming) | Fine, but they'll conflict with #219. Fold them into (or rebase them after) #219 rather than merging in arbitrary order. #223's description itself notes leftover dead lines (`myAlphaNumTestValue`, stray `let byteArray;`) — catch that in review. |
| #229 | Store payload as base64 (−33% size) | Requires §4 format versioning first. New pages get `formatVersion: 2`; `--decrypt` and `extractStaticryptConfig` branch on it. |
| #231 | gzip-compress before encrypting | Same gate as #229; stacks on it (`formatVersion: 3` or a `compression` flag in the config). Also review the `msgReader` callback pattern it introduces — it may be over-engineering for the API's string-based surface; buffers are likely fine once #219 is in. |
| #200 | `--overwrite` flag | Independent of this plan; CLI-only. If merged, keep the API string-based (overwrite is an fs concern, stays in CLI). |
| #242 | dependabot `form-data` bump | Dev-only dep; merge. |

Other internal notes for this layer:

- `codec.init(cryptoEngine)` dependency injection looks odd in Node but exists for the
  browser bundle (`convertCommonJSToBrowserJS` strips `require` lines, so `codec` must
  receive its engine at runtime). **Keep it**, but document the reason at the top of
  `codec.js` — it's the kind of thing a well-meaning refactor would "simplify" and silently
  break the generated pages.
- Same for the odd `/*[|variable|]*/0` template syntax — `formater.js` explains it, good;
  `staticryptJs.js:1-2` deserves a one-line pointer.

## 6. Template rendering robustness (small)

`renderTemplate` (`lib/formater.js:14-24`) silently substitutes the *variable name* when a
key is missing from `data`. A typo'd variable in a custom template, or a missing default,
produces a page that says `template_title` — or worse, an invalid `staticrypt_config` — with
no signal.

Spec: add an optional strict mode — `renderTemplate(template, data, { strict })`. The API
and CLI render the *default* template strictly (any unknown variable throws: it's our
template, unknowns are our bug); custom user templates render lenient with a
`console.warn` from the CLI listing unresolved variables. No behavior change for existing
custom templates.

Effort: tiny. Risk: none.

## 7. Packaging & DX

- **Fix `files`**: add `index.js`, `index.d.ts` (and keep `lib/password_template.html` —
  already under `/lib`).
- **Don't add a restrictive `exports` map** in a minor release — it would break deep
  requires (§0.5). Either omit it, or add one with a `"./*": "./*"` passthrough. Revisit in
  a major.
- **Stay CommonJS.** Dual ESM/CJS packaging is a maintenance tax and a compat minefield;
  ESM users can `import staticrypt from "staticrypt"` (CJS default interop) just fine.
  Document it.
- **README**: add a "Use as a library" section with the §1 examples; state explicitly which
  modules are public API (root entry + documented names) and that everything else is
  internal.
- **CI**: add the `npm pack` + require smoke test (§1). The test workflow already runs the
  suite on PRs.

## Suggested sequencing

Each step is independently shippable and keeps the tree green:

1. **Quick fixes** (no release needed): `copyFile` undefined-variable bug, top-level
   `.catch()` on `runStatiCrypt`, merge #242.
2. **§2 extract pure core + throw-don't-exit** — internal only.
3. **§3 traversal rewrite** — internal only.
4. **§4 payload module + format versioning** — internal only, adds `formatVersion` to new
   output (old decoders ignore unknown keys; verified by fixtures).
5. **§1 public API + types + README + §6 strict rendering** → **minor release** (e.g. 3.6.0).
   CLI now runs on the API.
6. **§5 perf series**: #227 → #219 (folding #214/#221/#223/#225) → #229 → #231, each gated
   on the compat fixtures, format bumps per §4. Minor releases as they land.

Steps 2–4 are pure refactors safeguarded by the existing test suite; step 5 is additive;
step 6 is where the community PRs land safely. Nothing in the plan requires a major version
or breaks any surface listed in §0.
